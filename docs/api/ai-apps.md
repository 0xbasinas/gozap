# AI apps (MCP)

How an AI assistant is allowed to read an account: OAuth sign-in, consent, and the `/api/mcp` endpoint.

## AI apps (MCP): sign in with OAuth, then call `/api/mcp`

An AI assistant (Claude, ChatGPT, an IDE) can be allowed to read a person's account. It signs in the way any OAuth 2.1 app does, and then calls `POST /api/mcp` with a bearer token. Everything runs on our own Worker and database; no hosted service is involved.

How it works:

- **Better Auth's `mcp()` plugin is the OAuth server** (never add `oauthProvider()` next to it). It needs `jwt()` for signing keys and `disabledPaths: ['/token']`. Tokens are signed JWTs (Ed25519); the keys live in the `jwks` table.
- **Apps identify themselves with a metadata document** (CIMD, `@better-auth/cimd`): the `client_id` is the https address of a JSON file the app publishes. Nobody can register a client by hand or by dynamic registration; `clientPrivileges` and `resourcePrivileges` lock Better Auth's client-admin endpoints to staff. Only staff may read the list, nobody may create.
- **Fetching that document is the risky part.** `src/cimdFetch.ts` allows https only, a public host name (no IP address, local name, port or login), no redirects, 5 seconds and 64 KB. A Worker cannot pin the resolved address, as Better Auth's docs suggest; its requests leave from Cloudflare's network, so private networks are out of reach anyway.
- **Sign-in and consent.** `/api/auth/oauth2/authorize` sends a signed-out person to `/sign-in` with a signed copy of the request; after sign-in (including the email link, whose `callbackURL` is the authorize address) the browser returns to authorize, which sends it to `/consent`. The page posts to `/api/auth/oauth2/consent`. People see and remove what they approved under "Connected apps" on the account page (`get-consents`, `delete-consent`).
- **Discovery documents** live at the site root (`/.well-known/oauth-authorization-server/api/auth`, `/.well-known/oauth-protected-resource/api/mcp`). `wrangler.jsonc` sends those paths to the Worker (`run_worker_first`), and `index.ts` rewrites them to `/api/__discovery/...`.
- **`/api/mcp`** checks the token against our own signing keys read in the same Worker (not by calling our own address), requires the `mcp:read` scope and the `azp` claim, then looks the person up so a suspension takes effect at once. The tools (`src/mcpServer.ts`) are read-only and limited to the person the token was issued to: `whoami`, `list_teams`, `list_devices`, `recent_security_activity`. It speaks the 2026-07-28 protocol only (`legacy: 'reject'`); requests need the `Mcp-Method` header, and `Mcp-Name` for tool calls.
- **Housekeeping.** Approval and removal are in the security activity (`app_connected`, `app_disconnected`) and the data export (`connectedApps`, never the tokens). All OAuth rows cascade with the account. The daily job removes expired tokens (`src/oauthPrune.ts`). Refresh tokens rotate and an old one stops working at once, and the database keeps only a hash of them (a test checks that the stored value is not the token). Access tokens are signed JWTs and are not stored at all.

- **Cutting an app off.** Suspending a person, deprovisioning them through SCIM and "Sign out everywhere" all delete their app tokens and approvals (`revokeAppAccess`). `/api/mcp` also re-checks the suspension on every call.
- **Abuse limits.** `/oauth2/authorize`, `/oauth2/public-client` and `/oauth2/token` have tighter rate limits than the rest of the API, because they can make the Worker fetch an app's address. The consent page shows the address the app is served from next to its self-chosen name.

- **DPoP.** An app can ask for tokens bound to its own key (`dpop_bound_access_tokens` in its metadata document). Such a token is refused as a plain bearer token and needs a fresh proof on every call, so a copied token alone is useless. Apps that do not ask get ordinary bearer tokens (most assistants do not support DPoP yet).
- **Device code.** An app without a browser starts at `/api/auth/device/code`, shows a short code, and the person types it at `/device` while signed in. The page names the app and its address and what it asks for first, because a code handed over by someone else is how this flow is abused. `/device/code` has its own tight rate limit. Pending approvals have no foreign key to the person, so account deletion and the daily clean-up remove them (`oauthPrune.ts`).
- **Write tool.** `sign_out_device` exists only for a token that carries the `mcp:write` scope, which the person sees on the consent page. It can only sign out the token's own person's devices and is recorded in the security activity. An app that calls it with a read-only token gets a step-up answer, not "no such tool": HTTP 403 with `WWW-Authenticate: Bearer error="insufficient_scope", scope="mcp:write", resource_metadata="..."` (RFC 6750), so a well-behaved client can ask the person to approve again with the extra permission. Better Auth's own `createInsufficientScopeError` is not exported from the packages we use, so `src/mcpServer.ts` builds the same challenge by hand.
- **Staff list and switch.** Admins (not support) see every app that has asked for access on the admin page ("AI apps": name, address, how many people approved it) and can switch one off or on (`GET /api/admin/ai-apps`, `POST /api/admin/ai-apps/disable|enable` with `{ clientId }`; ours, because the plugin's `disabled` flag can only be set from inside the server). Switching off sets `disabled` (the plugin then refuses it at authorize, token, introspect and userinfo), deletes its tokens, approvals and pending device codes in one batch, and `/api/mcp` refuses its still-valid access tokens at once (`isAiAppDisabled`, one indexed read). Switching on starts clean: each person approves again. Both are recorded (`ai_app_disabled`, `ai_app_enabled`, with the staff member as actor and the app address kept in the row's detail, not shown to people). `clientPrivileges` stays admin-only and never allows `create`.
- **Extra plugin endpoints.** All of the plugin's `/oauth2/*` routes are served under `/api/auth`. `introspect` and `revoke` need the caller's client credentials (strangers get a 4xx) and now have their own limit (20 a minute per address); `register` is refused and limited to 5. `end-session` (RP-initiated logout) is **not offered** (404): no AI app uses it, and for an unknown app id it made the Worker fetch that address for a stranger and answer 500. `refreshTokenReuseInterval` stays `0`. `list_teams` is one of the MCP read tools above.
- **Pinned to 1.7.x.** `src/betterAuthVersion.test.ts` fails if any Better Auth package leaves 1.7.x, so a `^1.7.x` range cannot move to 1.8 unnoticed (release notes first, as TODO.md says).

Not built: more write tools, and pinning the resolved address of an app's metadata document (a Worker cannot do it; the limits in `cimdFetch.ts` stand in for it, and a Worker cannot reach private networks anyway).

**SCIM only touches addresses at proven domains.** A directory can create, adopt or re-address a sign-in account only when the address is at a domain the team has proven by DNS (a verified company sign-in). Otherwise it gets 403. Without this, anyone who could start a team could pre-create accounts for strangers' addresses, suspend an address before its owner signed up, or move an account that someone later signed in to onto an address they control. Changing an account's address also signs out its existing sessions.
